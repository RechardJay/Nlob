# C风格字符串 cstr

我们都知道：C语言并没有真正的字符串，所有字符串都是字符数组；声明一个字符串字面量，实际是创建了一个 `char[]`，它自动以 `0` 结尾标志结束。

```rust
char* s = "hello,world!"
```

上面的这条语句，分配的多少内存？

在C中，指针的大小等于字长。对于常见的64位机器，一个指针是8字节，而一个char（unsigned short）占用一个字节。我们有一个char*和一个 `12 `个字节的数组：s 是一个8字节的char*，它指向字符串的开头；如果对它解引用，会得到字符 `h` 。而这个字符串，实际占用了`13`个字节，别忘了结尾的 `0` 。所以这条语句至少占用了 21 字节。

那下面两条语句呢？需要分配多少内存

```rust
char* s1 = "hello,world!"
char* s2 = "hello,world!"
```

答案是29。因为编译器做了一个聪明的事情：你重复声明了同一个字符串，第二个字符串不会再分配内存了，而是直接复用已有的数据。s1和s2实际指向了同一地址。 证据是 `printf("%ld",s)` s1和 s2 的值一样。这一切都在编译期完成，编译期的写死的字符串称为字符串常量，字符串常量会被复用，有的语言称这种机制为字符串常量池、静态区。

之所以叫字符串常量，是因为编译器分配的字符串是不可变。

```rust
char* s = "hello,world!"
//s[0] = 'S';
//*s = 'H';
```

如果你企图通过s去修改字符串，你会得到段错误，因为这块内存只读。字符串常量只读有两个考量：要在编译器确定内存的大小的位置，就不能用堆栈，所以字符串常量放在数据段，数据段天然不可修改；其次只读也保证了复用，多个变量共享这款内存，read-only能杜绝一致性问题；

除了读取，唯一操作字符串常量的方式就是复制：把他们复制到堆中，然后随你折腾。 完成这件事的函数是 strdup，他返回一个可以写入的字符串，当然这是一个char[]，在堆中。

再看这条语句，多少内存？答案是34

```c++
char s[] = "hello,world!"; 
```

char s[] 和 char* s 都占据 8字节，s[]本身也是指针；但区别在于 s[] 发生了一次拷贝，数组默认分配在栈上，其内容和大小是对字符串字面量的拷贝，因此这里有额外的开销。好处是栈上的字符数组时可变的。

总之如果你想掌控字符串读写的话，拷贝和动态分配堆内存是必要的。但大部分时候，字符串是只读的，此时的拷贝便是额外开销。

不要批评C的字符串很糟糕，因为它根本就没有字符串。它只是努力地将字符串数组当做字符串来用，并提供了一堆函数来完成这场Cosplay，记得#include<string.h>。

使用cstr时时刻提醒自己：数组在哪里、是否可变；

# C++ 字符串

首先，C++兼容C风格字符串。因此上面的一切仍然适用。

好消息是：C++有了真正的字符串：太好了时std::string，我们有救了…吗？

先不提封装的一大堆函数，string对象自己携带了重要的东西：len/size 。

这是我们最关心字符串的两件事：

- 长度是字符串的一部分，我们不用再把长度和指针分开传递了。

- string对象持有一份字符串的拷贝，这是在构造时进行的。拷贝意味着：数据是可变的，这是我们自己的副本；额外开销；

使用std::string吧！好消息是：不用传长度了；坏消息时，一个string对象可能会很大，这是私有拷贝的代价。如果你传递/返回了一个大string对象却没加&，那么恭喜你在无意间放飞了内存。

为了兼容C，std::string背负了太多太多；比如虽然已经存储了长度size，但仍然以 0结尾。

## std::string_view

现代C++引入的string_view，用于解决string拷贝开销问题。众所周知：绝大多数字符串只读就够了，默认拷贝是愚蠢的。因此string_view 不会拷贝数据：它仅仅持有我们最关系的两个东西：data* 和 len，这能省不少内存，同时支持不少操作比如拷贝和截取。大胆的创建并传递string_view吧！

# 其他语言的字符串

## Java String

Java 的String用起来是最省心的：它就是一个简简单单的不可变的对象。你可以像使用基本类型一样使用它而无需导入，不用传长度，不用担心指针越界、隐式拷贝和生命周期。况且我都用Java了还担心什么内存啊，JVM启动就200MB了，差你这点字符串的内存吗。

别忘了一切皆对象，包括我们声明的字符串常量。

```java
String s = "hello";
```

注意到s仍是一个对象，因为你可以对s调用字符串的所有方法；编译器将由字符串字面量创建的对象同一放在字符串常量池中以实现复用。

再次强调String是不可变，对String的操作会返回新String；

String 重载了 + ，s1 + s2 同样返回新字符串；注意频繁拼接会产生大量字符对象，不要这样做；可变字符串使用StringBuffer、StringBuilder

## 后来居上

新生代语言们身上处处有前辈的影子。

### Go

Go字符串是一个只读的字符串数组；构造后不可变；

字符串字面量会放入静态区复用

用string()显示构造字符串会做拷贝；

字符串原生支持切片操作，无拷贝零开销；切片在Go中有单独的类型，不持有数据本体仅有引用。

重载+，创建新字符串；动态拼接用Strings.Builder。

没有可变字符串，请用 byte[]

### zig

zig 没有字符串类型，请看 []u8 + ‘0’；

zig没有隐式控制流，一切交给程序员：可变、拷贝全看开发者：加不加const、如何分配内存；

数组原生支持切片语法； 

### Rust

Rust的字符串最为复杂，但注意其复杂度来源于语言本身而非字符串设计。

Rust中有两种字符串类型：String 、&str

String 是可变的Vec<u8> 包装；&str是不可边的char*+len。

rust的String\&str都不能看做字节数组，因为有UTF8保证，一个字符不一定是一个字节；

&str支持切片

# 字符串设计小结

看了这么多，似乎并没有发现让人满意的设计。毕竟no free launch，一切的设计都是权衡。

人类的需求是高级、复杂的高度抽象，计算机则低级的指令序列+字节数组。这些矛盾在在名为字符串的战争爆发，语言想当个好媳妇就得两头挨骂。

C的抽象程度过低，想在低级的抽象中设计一个字符串是困难的，C选择的一个简单的方式，然后失败了。它偷懒的代价是被骂了50年。所有人讨厌cstr却又不得不接受它。

zig的设计无意明智的，前车之鉴后事之师，底层抽象不做高级封装。

C++，为兼容cstr而付出了惨痛的代价，即便如此std::string也没有让人满意，std::string_view 在C++17才引入，约等于没有。string如此常用的类型既然支持了为何还要手动导入声明。唉，算球，C++的缺点太多了，以至于不差这一个。这是我全都要的代价。

现代语言的一个标志性设计是切片slice：不可变视图、胖指针。字符串原生切片操作是一个伟大的设计，如果没有生命周期问题的话…GC、所有权语义，还是未定义行为？
